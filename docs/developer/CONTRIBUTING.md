# Як приєднатися до розробки

Цей документ описує, як вносити зміни так, щоб документація не відставала від коду. Головний принцип: **docs-or-don't-merge** (немає оновленої документації, немає злиття).

## Потік змін

1. Створіть гілку від `main` (`feature/...`, `fix/...`, `docs/...`).
2. Змініть код і **у тому самому PR (pull request, запит на злиття)** оновіть документацію за таблицею нижче.
3. Перед пушем запустіть локальні перевірки (розділ «Як перевірити локально»).
4. Відкрийте PR. Шаблон PR містить чек-лист нижче, галочки в ньому ставить автор.
5. Конвеєр `Docs` (GitHub Actions) має бути зеленим. Червоний конвеєр означає, що злиття заблоковане до виправлення.
6. Після злиття в `main` сайт публікується на GitHub Pages автоматично.

## Чек-лист docs-or-don't-merge

PR зі зміною публічної поведінки (маршрут, формат відповіді, змінна середовища, схема даних, порядок запуску) не зливається, поки не виконано всі пункти:

- [ ] Змінено API: оновлено `docs/api/openapi.yaml`, Spectral без помилок
- [ ] Змінено компоненти, маршрути чи модель даних: оновлено `docs/architecture/sdd.md`
- [ ] Змінено середовища, змінні, CI/CD чи відновлення: оновлено `docs/architecture/isd.md` та `.env.example`
- [ ] Змінено архітектурне рішення: створено новий ADR (старий отримав `Superseded by`), старий не переписано
- [ ] Змінено поведінку для користувача чи запуск: оновлено `README.md`
- [ ] Додано запис у `CHANGELOG.md` (розділ `Unreleased`)
- [ ] У зачеплених сторінок оновлено `review_date` у паспорті
- [ ] Локальні перевірки пройдені, конвеєр `Docs` зелений

## Чек-лист надійності (failure-mode)

Додано за результатами аналізу інциденту INC-001 ([Post-Mortem](../incidents/INC-001-postmortem.md), дія CAPA-3). Коренева причина інциденту: процес не вимагав аналізу режимів відмови. PR, що змінює компонент зі станом (файли, БД, черги) або з викликом зовнішнього ресурсу, не зливається, поки не виконано обидва пункти:

- [ ] Описано, як компонент може відмовити (обрізаний файл, недоступний диск чи БД, паралельний доступ з кількох процесів), і є автотест на кожну з цих відмов, або в описі PR зазначено, чому тест не потрібен
- [ ] Збій допоміжної функції (журнал, історія, метрики) не ламає основний сценарій: помилка логується, запит користувача завершується успішно

Приклад виконання: `tests/test_history_utils.py` (відмови `history_utils.py`).

## Що оновлювати за типом зміни

| Що змінилося | Документ |
|---|---|
| маршрут `/api/*`, параметри, формат відповіді | `docs/api/openapi.yaml`, `docs/architecture/sdd.md` |
| компонент, модель даних | `docs/architecture/sdd.md` |
| змінна середовища, порядок запуску, CI/CD, відновлення | `docs/architecture/isd.md`, `.env.example` |
| вибір технології чи підходу | новий ADR у `docs/architecture/adr/` |
| поведінка для користувача | `README.md` |

## Як перевірити локально

```bash
npx --yes markdownlint-cli2@0.14.0 "docs/**/*.md" README.md   # розмітка
npx --yes @stoplight/spectral-cli lint docs/api/openapi.yaml   # контракт API
mkdocs build --strict                                          # посилання і збірка
python3 scripts/check_review_dates.py                          # актуальність паспортів
bash scripts/doc-audit.sh                                      # дрейф коду і документації
```

## Правила для ADR

ADR (Architecture Decision Record, запис архітектурного рішення) нумеруються послідовно й не переписуються заднім числом. Нове рішення оформлюється новим номером, а застаріле отримує статус `Superseded by ADR-NNNN`.

## Застарілі сторінки

Сторінка, яку замінив новіший документ, не видаляється одразу. У її паспорті ставиться `status: deprecated` і `superseded_by: <шлях до актуального документа>`, а на початку сторінки додається банер із посиланням на заміну. Так зовнішні посилання не ламаються, а читач бачить, куди йти далі. Аудит `scripts/check_review_dates.py` виводить такі сторінки окремим списком.

## Власники та версії

- Власників визначає `.github/CODEOWNERS`. Автоматичний запит на рев'ю працює завжди. Обов'язкове схвалення власника діє тільки після ввімкнення правила «Require review from Code Owners» у захисті гілки `main`.
- Стан документації фіксується анотованими тегами `docs-vMAJOR.MINOR`. Тег дає змогу відновити сайт у стані конкретної версії: `git switch --detach docs-v1.0`.
