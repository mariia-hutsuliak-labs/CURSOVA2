# RB-001: Відновлення бази даних PostgreSQL з резервної копії

| Поле | Значення |
|---|---|
| Ідентифікатор | RB-001 |
| Операція | Відновлення БД `bookstore` з дампа `pg_dump` і повернення застосунку в роботу |
| Рівень автоматизації | **1 (скриптований)** за шкалою Лекції 10: 0 ручний, 1 скриптований, 2 «одна кнопка», 3 self-healing |
| Цільовий час виконання | не більше 30 хвилин (запас відносно RTO 4 години з [ISD §7](../architecture/isd.md)) |
| Пов'язані документи | [ISD](../architecture/isd.md) (RTO/RPO, backup policy), [slo.yaml](../slo.yaml), [maintenance-plan](../maintenance-plan.md) |

## 1. Тригер: коли застосовувати

Runbook запускається, коли спрацював один із алертів з розділу 8 (кожен тригер має алерт, а кожен алерт посилається на цей runbook):

| Тригер | Алерт з каталогу |
|---|---|
| БД недоступна понад 1 хвилину і не піднімається перезапуском сервера PostgreSQL | ALR-002 |
| У журналі застосунку серія помилок `ERROR` рівня БД (пошкоджені або зниклі таблиці) | ALR-003 |
| Сторінка `/login` не відповідає 200 через неробочу БД | ALR-001 |
| Планове розкладання: щоквартальне тестове відновлення (restore drill, розділ 9) | немає алерта, запускається за календарем |

## 2. Передумови

- Доступ до машини, де працює PostgreSQL, і права на створення та видалення БД (роль `postgres` або власник кластера).
- Встановлені клієнтські утиліти PostgreSQL: `pg_restore`, `psql` (перевірка: `pg_restore --version`).
- Файл `.env` у корені проєкту з коректним `DATABASE_URL` (формат SQLAlchemy `postgresql+psycopg2://USER:PASSWORD@localhost:5432/DBNAME`; утиліти PostgreSQL приймають URL без `+psycopg2`, тому команди нижче його вирізають).
- Наявний дамп формату custom (`pg_dump -Fc`) у каталозі `backups/`, не старший за 24 години (RPO).
- Права на запуск і зупинку процесу застосунку.

## 3. Покрокові дії

Усі команди виконуються з кореня проєкту.

**Крок 1. Зафіксувати час початку і зупинити застосунок** (щоб він не писав у БД під час відновлення):

```bash
date -u +"%Y-%m-%dT%H:%M:%SZ"
pkill -f "python app.py" || true
```

**Крок 2. Вибрати дамп і перевірити, що він читається:**

```bash
DUMP=$(ls -t backups/bookstore_*.dump | head -1)
echo "Використовується: $DUMP"
pg_restore --list "$DUMP" | head -5
```

Якщо друга команда повертає помилку, дамп пошкоджено: візьміть наступний за часом (`ls -t backups/bookstore_*.dump`).

**Крок 3. Зберегти аварійну копію поточного стану БД** (якщо БД ще відповідає; якщо ні, крок пропускається):

```bash
set -a; . ./.env; set +a
pg_dump -Fc "${DATABASE_URL/+psycopg2/}" -f "backups/pre_restore_$(date -u +%Y%m%dT%H%M%SZ).dump" || echo "БД недоступна, пропускаю"
```

**Крок 4. Відновити БД одним скриптом** (він перестворює БД, робить `pg_restore` і виводить кількість рядків у `users`, `products`, `sales`):

```bash
bash scripts/restore-db.sh "$DUMP"
```

**Крок 5. Відновити історію запитів** (каталог `history/`, копіюється разом із дампом, див. [ISD §4](../architecture/isd.md)):

```bash
LATEST_HISTORY=$(ls -t backups/history_*.tar.gz | head -1)
tar -xzf "$LATEST_HISTORY" -C .
```

**Крок 6. Запустити застосунок:**

```bash
nohup python app.py > app.log 2>&1 &
sleep 5
```

## 4. Верифікація: як переконатися, що ціль досягнута

```bash
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5000/login
tail -n 20 app.log | grep -c ERROR
```

Критерії успіху:

1. Перша команда друкує `200`.
2. Друга команда друкує `0` (у свіжому журналі немає рядків `ERROR`).
3. Кількість рядків із кроку 4 (`users`, `products`, `sales`) збігається з контрольними значеннями, зафіксованими в журналі резервних копій на момент створення дампа.
4. Вхід під `operator` проходить, а сторінка `/api/query10` відкривається без помилки.

Якщо хоча б один критерій не виконано, переходьте до розділу 5.

## 5. Відкат

Відкат повертає систему до стану безпосередньо перед початком runbook (використовується аварійна копія з кроку 3):

```bash
pkill -f "python app.py" || true
PRE=$(ls -t backups/pre_restore_*.dump | head -1)
bash scripts/restore-db.sh "$PRE"
nohup python app.py > app.log 2>&1 &
```

Якщо аварійної копії немає (БД була недоступна на кроці 3), відкату немає: беріть попередній за часом дамп із кроку 2 і повторіть кроки 4 і 6.

## 6. Ескалація

| Умова | Кому | Таймаут |
|---|---|---|
| Крок 4 не завершився за 15 хвилин або `pg_restore` повертає помилки | L2: власник системи (Mariia Hutsuliak) | одразу |
| Усі наявні дампи пошкоджені | L3: DBA / викладач-куратор, і повідомити про можливу втрату даних понад RPO | одразу |
| Верифікація (розділ 4) не пройдена після відкату | L2, оголосити інцидент SEV-1 за [maintenance-plan](../maintenance-plan.md) | 5 хвилин |
| Загальний час відновлення перевищив 2 години (половина RTO) | L2, попередити бізнес про ризик порушення RTO | 2 години |

## 7. Обґрунтування рівня автоматизації

Обрано **рівень 1 (скриптований)**. Операція рідкісна (аварійна або квартальна), але критична за наслідками, а помилка людини о третій ночі (не той дамп, не та БД, забутий крок) обходиться дорого. Тому ключову частину (перевірка дампа, перестворення БД, `pg_restore`, контрольні кількості рядків) винесено в `scripts/restore-db.sh`, а рішення людини (який дамп, чи зупиняти застосунок, чи робити відкат) лишено в runbook. Рівень 2 («одна кнопка») не виправданий: вибір дампа і підтвердження знищення поточної БД мають лишатися свідомим рішенням людини. Рівень 3 (self-healing) небезпечний: автоматичне перезаписування бойової БД без людини може знищити свіжі дані, які ще не потрапили в дамп.

## 8. Каталог алертів моніторингу

Статус: алерти специфіковано, але не налаштовано в системі моніторингу (ISD §6 позначає моніторинг як ціль). Налаштування входить у план CAPA / Maintenance Plan.

| ID | Назва | Умова спрацювання | Серйозність | Відповідальна роль | Runbook |
|---|---|---|---|---|---|
| ALR-001 | Login page down | `GET /login` повертає не 200 або не відповідає 10 с, 3 перевірки поспіль (перевірка щохвилини) | SEV-2 | L1 черговий | [RB-001](RB-001.md) |
| ALR-002 | Database unreachable | PostgreSQL недоступний понад 1 хвилину (після вичерпання retry: 3 спроби, backoff 0.3 с, множник 2) | SEV-1 | L2 власник системи | [RB-001](RB-001.md) |
| ALR-003 | DB error burst | понад 5 записів `ERROR` рівня БД у журналі за 5 хвилин | SEV-2 | L1 черговий | [RB-001](RB-001.md) |
| ALR-004 | Backup stale | з часу створення останнього дампа минуло понад 26 годин (RPO 24 години плюс запас) | SEV-3 | L1 черговий | [RB-001](RB-001.md), розділ 9 |

## 9. Procedure: тестове відновлення (restore drill)

Резервна копія, відновлення з якої ніколи не перевірялося, резервною копією не вважається. Раз на квартал (і після кожної зміни схеми БД) виконується відновлення в окрему БД, бойові дані не чіпаються:

```bash
DUMP=$(ls -t backups/bookstore_*.dump | head -1)
bash scripts/restore-db.sh "$DUMP" --target bookstore_drill
```

Drill успішний, якщо скрипт завершився кодом 0 і кількість рядків у `users`, `products`, `sales` збігається з контрольними значеннями дампа. Результат (дата UTC, ім'я дампа, тривалість, висновок) записується в журнал drill в [ISD](../architecture/isd.md).
