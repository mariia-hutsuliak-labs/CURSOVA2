# План CAPA для INC-001

CAPA (Corrective and Preventive Actions, коригувальні та попереджувальні дії) перетворює висновки [Post-Mortem](INC-001-postmortem.md) на конкретні зміни.

- **Коригувальна дія** усуває причину збою, який **уже стався** (щоб саме цей інцидент не повторився).
- **Попереджувальна дія** усуває причину **потенційного** збою, виявленого аналізом (щоб схожі інциденти не сталися в інших місцях).

Головне поле кожної картки: **перевірка ефективності** (effectiveness check), тобто як і коли буде доведено, що дія працює, а не лише що її виконано.

## CAPA-1 (коригувальна): атомарний запис і самовідновлення при читанні

| Поле | Значення |
|---|---|
| Опис | У `history_utils.py`: `save_history` пише у тимчасовий файл, зберігає його на диск (`fsync`) і підміняє основний через `os.replace`, тому читач ніколи не бачить частково записаний файл. `load_history` при пошкодженому JSON переносить файл у `user_<id>.json.corrupt-<UTC-час>` (збереження доказу) і починає історію заново. Експорт персональних даних читає в режимі `strict=True`, щоб повідомити про неповноту. Видалення при анонімізації прибирає і карантинні копії |
| Власник | Mariia Hutsuliak |
| Дедлайн | 2026-11-17 |
| Статус | виконано (причину усунуто фактично, зміни в коді) |
| Перевірка ефективності | **1.** Автотести `tests/test_history_utils.py` (9 тестів): обрізаний файл переноситься в карантин, невдала заміна лишає старий файл цілим, тимчасових файлів не залишається. **2.** Повторна симуляція INC-001 на виправленому коді (`INC-001-pass.log`, 2026-11-17 21:20 UTC): 0 помилок із 20 запитів, пошкоджений файл перенесено автоматично. **3.** Контроль через 30 діб (2026-12-17): у журналі застосунку записи `[HISTORY] Пошкоджений файл` не супроводжуються жодним HTTP 500 на `/api/query*` і `/my_history`. Критерій успіху: кількість таких 500 дорівнює 0 |

## CAPA-2 (коригувальна): ізоляція збою журналу від основного сценарію

| Поле | Значення |
|---|---|
| Опис | `add_history_entry` обгорнуто так, що жодна помилка запису історії не виходить за межі функції: збій логується (`logger.exception`), функція повертає `False`, а звіт користувачеві віддається. Допоміжна функція більше не стоїть на критичному шляху 13 викликів у 11 маршрутах |
| Власник | Mariia Hutsuliak |
| Дедлайн | 2026-11-17 |
| Статус | виконано |
| Перевірка ефективності | **1.** Автотест `test_add_entry_never_raises_when_storage_fails`: при `OSError` у сховищі виклик повертає `False` і не кидає винятку (до виправлення цей тест падав). **2.** Ручна перевірка відмови диска **2026-11-24**: зробити каталог `history/` недоступним для запису (`chmod 555 history`), виконати `GET /api/query6`, очікувати 200 і запис `[HISTORY] Не вдалося записати` в журналі, потім повернути права (`chmod 755 history`). **3.** Контроль через 30 діб: HTTP 500 на аналітичних маршрутах, спричинених історією, дорівнюють 0 |

## CAPA-3 (попереджувальна): обов'язковий аналіз режимів відмови в Definition of Done

| Поле | Значення |
|---|---|
| Опис | Усуває кореневу причину з Why 5. Правило «для кожного компонента зі станом або з викликом зовнішнього ресурсу описати, як він відмовляє, і написати тест на цю відмову» додано до чек-листа PR (`.github/pull_request_template.md`), до [CONTRIBUTING](../developer/CONTRIBUTING.md) (розділ «Чек-лист надійності») і до таблиці Definition of Done в `README.md`. Потенційно уразливі компоненти, що ще не перевірені за цим правилом (`privacy/audit.py`, `privacy/consent.py`, outbox-повідомлення), внесено в [план підтримки](../maintenance-plan.md) |
| Власник | Mariia Hutsuliak |
| Дедлайн | 2026-12-01 (аналіз відмов решти компонентів зі стану) |
| Статус | у роботі: правило введено 2026-11-17, огляд решти компонентів до дедлайну |
| Перевірка ефективності | Дію вважаємо ефективною, якщо: **1.** у перших трьох PR після 2026-11-17, що змінюють компонент зі станом, заповнено обидва пункти чек-листа надійності і є тест на відмову (контроль 2026-12-15 за історією PR); **2.** до 2026-12-01 для кожного з компонентів зі списку в плані підтримки є запис про режими відмови і щонайменше один тест. Якщо у PR пункт пропущено, правило визнається неефективним і посилюється автоматичною перевіркою в CI |
