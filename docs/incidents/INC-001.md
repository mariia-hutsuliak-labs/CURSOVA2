# Incident Report INC-001: відмова сторінок аналітики через пошкоджений файл історії

Incident Report (звіт про інцидент) фіксує факти збою: що, коли, хто постраждав і як усунули. Причини аналізує окремий документ Post-Mortem; тут лише хронологія і вплив. Усі часові мітки в **UTC** (Coordinated Universal Time, єдиний годинник для всіх записів). Київський час на момент інциденту: UTC+2.

## 1. Зведення

| Поле | Значення |
|---|---|
| Ідентифікатор | INC-001 |
| Тип | контрольована симуляція (учбовий інцидент), середовище dev |
| Компонент | legacy-модуль `history_utils.py` (див. [документацію компонента](../legacy/history-utils.md)), файл `history/user_2.json` користувача `operator` |
| Механізм збою | файл історії обрізано посеред JSON (імітація аварійного завершення під час запису, борг TD-2) |
| Серйозність | **SEV-2** (обґрунтування в розділі 2) |
| Початок (UTC) | 2026-11-17 21:03:13 |
| Кінець, стабілізація (UTC) | 2026-11-17 21:03:24 |
| Тривалість | 11 секунд (у симуляції; у реальному середовищі без моніторингу тривалість обмежена лише тим, коли про збій дізнаються) |
| Джерело даних | `reports/incident/INC-001-timeline.log`, створений скриптом `scripts/incident_sim.sh` |

## 2. Серйозність за матрицею впливу

| Рівень | Критерій | Тут |
|---|---|---|
| SEV-1 | повна недоступність системи, втрата або витік даних | ні: застосунок працює, `/login` відповідає 200, дані БД не постраждали |
| **SEV-2** | ключова функція недоступна для групи користувачів, автоматичного обходу немає | **так**: для користувача `operator` усі аналітичні звіти (`/api/query6`) і сторінка `/my_history` повертають 500; автоматичного обходу немає, потрібне ручне втручання |
| SEV-3 | часткова деградація, є прийнятний обхід | ні: обхід існує, але ручний |

Оцінка SEV-2 враховує, що постраждав один файл, а отже один користувач (з 4 в системі), але саме той, хто працює зі звітами щодня, і що збій не лікується сам.

## 4. Виконані дії і тимчасовий обхід

1. Перевірено, що збій локальний: `/login` працює, інші сторінки без залежності від історії не зачеплені.
2. Збережено доказ: пошкоджений файл не видалено, а переміщено в `reports/incident/` (він знадобиться для Post-Mortem).
3. Тимчасовий обхід: відсутність файлу `load_history` сприймає як порожню історію (повертає `[]`), тому модуль створює новий файл при наступному записі. Ціна обходу: історія запитів цього користувача скидається.
4. Перевірено стабілізацію обох ендпоінтів.

Постійного виправлення в цьому звіті немає: воно належить до плану CAPA.

## 6. Порушення SLA і витрата Error Budget

Порівняння зі специфікацією [slo.yaml](../slo.yaml) (вікно 30 діб, 43 200 хвилин):

| SLI | SLO | SLA | Бюджет за SLO | Витрачено цим інцидентом | Висновок |
|---|---|---|---|---|---|
| SLI-1 Availability | 99,5% | 99,0% | 216 хв | 0,18 хв (близько 0,085% бюджету) | SLO і SLA **не порушено** |
| SLI-2 Latency `/api/query6` | 95,0% | 90,0% | 2160 хв | помилки 500 до швидкості не належать | не порушено |
| SLI-3 First-attempt success | 99,0% | 97,0% | 432 хв | механізм retry не спрацьовував (збій не в БД) | не порушено |

Висновок: на місячному вікні порушення SLA немає, бо збій тривав лише 11 секунд. Але за 100% помилок у вікні інцидент у такому ж виді тривав би 216 хвилин (3,6 години), перш ніж бюджет SLI-1 за SLO вичерпався б, а при вичерпанні діє change freeze ([ccb-charter.md](../change-management/ccb-charter.md)). У реальному середовищі без моніторингу цей час визначає не обхід (кілька секунд), а затримка виявлення.

## 7. Факти про виявлення, які знадобляться для Post-Mortem

- У каталозі алертів [RB-001](../runbooks/RB-001.md) є ALR-001, що перевіряє `GET /login`. У цьому інциденті `/login` увесь час повертав 200.
- Виявлення було ручним: збій зафіксувало опитування, яке запустив черговий.
- Жоден тест не перевіряє поведінку `history_utils.py` на пошкодженому файлі.

Це спостереження, а не висновки: причинний аналіз виконується в Post-Mortem.

## 8. Стан у системі контролю версій

Стан інциденту (FAIL) зафіксовано комітом `ops(incident): capture legacy module outage, FAIL`. Стан після усунення причини (PASS) фіксується комітом `docs(maintenance): deliver capa actions and swebok plan, PASS`.
