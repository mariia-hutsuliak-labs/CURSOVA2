# ISD: специфікація інфраструктури (Infrastructure Specification Document)

Цей документ відповідає на питання «де і на чому система працює, як її розгорнути і відновити». Внутрішню структуру описано в [sdd.md](sdd.md).

Власник: Mariia Hutsuliak. Цикл перегляду: 90 днів (експлуатаційна документація), див. [maintenance.md](../developer/maintenance.md).

Позначки статусу: **[є]** реалізовано в репозиторії, **[ціль]** цільове значення, ще не реалізоване.

## 1. Топологія розгортання

Поточна топологія: **локальна**. Один процес Flask (`python app.py`, `debug=True`, порт 5000) і окремий сервер PostgreSQL на тій самій машині (`localhost:5432`). Контейнеризація застосовується лише для ізольованого раннера вимірювання метрик якості (`Dockerfile.quality`, `docker-compose.quality.yml`), а не для самого застосунку.

| Компонент SDD | Де запускається | Порядок підняття |
|---|---|---|
| PostgreSQL | локальний сервер або окремий контейнер | 1 (до застосунку) |
| `init_db.py` | одноразово, створює таблиці й початкових користувачів | 2 |
| Flask Web App (`app.py`, `models.py`, `analytics/`, `sale_values.py`, `inventory_alerts.py`, `resilience.py`, `privacy/*`, `templates/`) | `python app.py`. Перший крок старту: `validate_config()` перевіряє `LOW_STOCK_THRESHOLD` ще до підключення до БД; при помилці процес завершується | 3 |
| Історія запитів (`history_utils.py`) | каталог `history/` у корені проєкту, створюється застосунком | разом із застосунком |
| Журнал (`privacy/secure_logging.py`) | stderr, за потреби файл `LOG_FILE` | разом із застосунком |

## 5. CI/CD і контроль якості

**[є]** Конвеєр `.github/workflows/complexity.yml` («Complexity and Hotspots»).
Тригери: `push` і `pull_request`. Образ: `python:3.11`. Стадії: checkout з повною історією (`fetch-depth: 0`) → Radon 6.0.1 цикломатична складність у JSON → code churn за 90 днів (`git log`) → hotspot-матриця (`scripts/hotspots.py`) → вивантаження артефактів `complexity-reports`.

**[є]** Локальні Quality Gates (`scripts/hooks/pre-commit`, підключається `git config core.hooksPath scripts/hooks`): Gitleaks (блокує коміт із секретом) і Radon (блокує коміт, якщо цикломатична складність функції CC > 10).

**[є]** Статичний аналіз SonarQube (ЛР8): конфігурація `sonar-project.properties` (проєкт CURSOVA2, сервер `http://localhost:9000`, Python 3.9, виключення: tests, reports, history, templates); сервер піднімається локально, у CI не входить.

**[є]** Скрипти аудиту об'єктного дизайну (ЛР8): `scripts/ck_metrics.py` (метрики Chidamber-Kemerer і MOOD), `scripts/coupling_matrix.py` (матриця зв'язності), `scripts/lab8_crash_test.py` та `scripts/lab8_inheritance_test.py` (краш-тести); результати в `reports/lab8/`.

**[є]** Повторювані перевірки: `scripts/sca-audit.sh` (pip-audit, залежності), `scripts/secret-scan.sh` (повна історія на секрети), `scripts/measure-quality.sh` (метрики в Docker), `scripts/doc-audit.sh` (актуальність документації, ЛР10).

**[ціль]** Додати `scripts/doc-audit.sh` як обов'язкову стадію конвеєра, щоб злиття з дрейфом документації блокувалося.

## 6. Моніторинг

**[ціль]** Моніторинг поки не реалізований. Мінімальний набір: перевірка доступності `GET /login` (HTTP 200) кожну хвилину; сповіщення, якщо PostgreSQL недоступний понад 1 хвилину (застосунок уже має retry з backoff: 3 спроби, 0.3 с, множник 2); аналіз журналу на події рівня ERROR.

## 7. Резервне копіювання та відновлення (RTO/RPO)

| Показник | Цільове значення | Пояснення |
|---|---|---|
| RPO (Recovery Point Objective): допустима втрата даних | 24 години | щодобовий дамп; для навчальної книгарні втрата продажів за добу прийнятна, ручне відновлення можливе з паперових чеків |
| RTO (Recovery Time Objective): допустимий час відновлення | 4 години | час на розгортання нового сервера, відновлення дампа і перевірку |

**[ціль]** Відновлення: `createdb bookstore` → `pg_restore` (або `psql < dump.sql`) → `.env` з актуальним `DATABASE_URL` → `python app.py` → перевірка входу та `/api/query10`. Відкат релізу: `git checkout <попередній тег>` і перезапуск процесу; схема БД створюється `db.create_all()` без міграцій, тому зміна схеми потребує ручного узгодження (відомий ризик, див. [ADR-0001](adr/0001-postgresql-as-primary-store.md)).

## 8. Експлуатаційна документація (ЛР12)

Розділ описує, як систему розгортають, оновлюють, відновлюють і резервно копіюють. Покрокова інструкція відновлення БД окремо: [RB-001](../runbooks/RB-001.md). Контракт рівня послуг: [slo.yaml](../slo.yaml).

### 8.1. Розгортання версії

Поточна топологія локальна (розділ 1), тому «розгортання» означає оновлення коду на машині, де працює процес Flask.

```bash
git fetch --tags
git checkout <тег-версії>                 # тег з історії релізів, наприклад docs-v2.0
source .venv/bin/activate
pip install -r requirements.txt
pkill -f "python app.py" || true
nohup python app.py > app.log 2>&1 &
sleep 5
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:5000/login      # health-перевірка: очікується 200
grep -c ERROR app.log                                                      # очікується 0
```

Перед розгортанням обов'язково зробити свіжу резервну копію (`bash scripts/backup-db.sh`), щоб було до чого відкотитися. Відкат релізу: `git checkout <попередній тег>`, `pip install -r requirements.txt`, перезапуск процесу і та сама health-перевірка.

### 8.2. Оновлення з міграціями

Міграційного фреймворку в проєкті немає: `db.create_all()` створює лише відсутні таблиці й не змінює наявні (відомий ризик, [ADR-0001](adr/0001-postgresql-as-primary-store.md)). Тому оновлення зі зміною схеми виконується в такому порядку:

1. Прочитати в [CHANGELOG](../../CHANGELOG.md) розділ нової версії: чи є запис про зміну схеми (`ALTER TABLE`, нова колонка, нова таблиця).
2. Зробити резервну копію: `bash scripts/backup-db.sh`.
3. Перевірити SQL-міграцію на копії БД: `bash scripts/restore-db.sh backups/bookstore_<дата>.dump --target bookstore_staging`, потім виконати скрипт міграції на `bookstore_staging` і запустити `python -m pytest tests/` з `DATABASE_URL`, що вказує на неї.
4. Зупинити застосунок, виконати перевірений SQL на бойовій БД, розгорнути нову версію за пунктом 8.1.
5. Зворотність: кожна міграція має парний скрипт відкату. Якщо відкат SQL неможливий (видалення колонки), відкат виконується відновленням із копії кроку 2 за [RB-001](../runbooks/RB-001.md).

### 8.3. Відновлення після відмови: порядок підняття сервісів

Порядок визначається залежностями (застосунок без бази не стартує):

1. **PostgreSQL**: запустити сервер, перевірити `pg_isready -h localhost -p 5432` (відповідь `accepting connections`).
2. **База даних**: якщо дані втрачено, відновити з дампа за [RB-001](../runbooks/RB-001.md).
3. **Каталог `history/`**: відновити з архіву, що створювався разом із дампом.
4. **Застосунок Flask**: `python app.py`; перший крок старту `validate_config()` перевіряє `LOW_STOCK_THRESHOLD`.
5. **Перевірка**: `GET /login` повертає 200, вхід під `operator`, сторінка `/api/query10` відкривається.

### 8.4. Цільові RTO і RPO та їх розрахунок

**RPO (Recovery Point Objective, допустима втрата даних) = 24 години.** Розрахунок: RPO дорівнює інтервалу між копіями, а копії щодобові (повний `pg_dump` о 02:00 за київським часом). У найгіршому випадку збій стається за мить до наступної копії, і втрачається майже доба змін. Для навчальної книгарні це прийнятно, бо продажі дублюються паперовими чеками. Якщо бізнес вимагатиме менше, перехід на безперервне архівування WAL (Write-Ahead Log) дасть RPO у хвилини.

**RTO (Recovery Time Objective, допустимий час відновлення) = 4 години.** Розрахунок бюджету часу в найгіршому випадку:

| Етап | Бюджет | Пояснення |
|---|---|---|
| Виявлення збою | 15 хв | перевірка `/login` щохвилини, спрацювання алерта після 3 невдач |
| Реакція і рішення (вибір дампа, запуск RB-001) | 30 хв | черговий читає runbook |
| Підняття PostgreSQL або нової машини з нуля | 60 хв | встановлення сервера, `.env`, клон репозиторію |
| Відновлення даних | 5 хв | виміряно 2026-11-17: БД 9,8 МБ, дамп 128 КБ, `restore-db.sh` виконався за 0,24 с; закладено запас у 100 разів на зростання даних |
| Верифікація | 15 хв | розділ 4 RB-001 |
| Разом | близько 2 год 05 хв | запас ≈ 1 год 55 хв відносно 4 годин на непередбачені затримки |

Висновок: ціль RTO 4 години досяжна з двократним запасом; вузьке місце не відновлення даних, а підготовка середовища.

### 8.5. Політика резервного копіювання (backup policy)

| Параметр | Значення | Статус |
|---|---|---|
| Обсяг даних | БД ≈ 9,8 МБ (дамп формату custom 128 КБ), `history/` 24 КБ (архів); виміряно 2026-11-17 | [є] |
| Типи копій | щодоби повна логічна копія `pg_dump -Fc` плюс архів `history/`. Інкрементних копій немає: `pg_dump` їх не підтримує, а на такому обсязі повна копія займає секунди. Інкрементне архівування WAL вводиться, якщо БД виросте понад 1 ГБ | [є] скрипт `scripts/backup-db.sh`, [ціль] розклад cron о 02:00 |
| Строк зберігання (retention) | 7 щоденних локально (автоматична ротація в скрипті); 4 щотижневих і 3 щомісячних у зовнішньому сховищі | [є] локальна ротація, [ціль] решта |
| Шифрування | AES-256 (`openssl enc -aes-256-cbc -pbkdf2`), парольна фраза в `BACKUP_PASSPHRASE` у `.env`; на зовнішні носії потрапляють лише зашифровані копії | [є] у скрипті |
| Правило 3-2-1 | **3 копії**: бойова БД, локальний дамп у `backups/`, зашифрована копія на зовнішньому носії. **2 типи носіїв**: внутрішній диск ноутбука та зовнішній SSD. **1 копія поза майданчиком**: зашифрований архів у хмарному сховищі | [ціль], зараз виконано лише локальну копію |
| Каталог `backups/` | у `.gitignore`: дампи містять дані й хеші паролів, у репозиторій не потрапляють | [є] |

### 8.6. Процедура тестового відновлення (restore drill)

Резервна копія, відновлення з якої ніколи не перевірялося, резервною копією не вважається. Drill виконується щокварталу і після кожної зміни схеми БД; повна процедура в [RB-001, розділ 9](../runbooks/RB-001.md).

Журнал drill:

| Дата (UTC) | Дамп | Куди відновлено | Тривалість | Контрольні значення | Висновок |
|---|---|---|---|---|---|
| 2026-11-17 | `bookstore_2026-11-17.dump` | `bookstore_drill` | 0,24 с | users=4, products=10, sales=1508 | успішно |
