# ADR-0001: PostgreSQL як основне сховище даних

- **Номер:** 0001
- **Статус:** Accepted (прийнято)
- **Дата фіксації:** 2026-11-14 (ретроспективний запис рішення, прийнятого на старті проєкту у вересні 2026)
- **Власник:** Mariia Hutsuliak

## Контекст

Система книгарні має зв'язані сутності (товари, продажі, поставки, договори, працівники) і потребує транзакційної цілісності: продаж одночасно створює рядки `sale_items` і зменшує `products.stock_quantity`. Потрібні складні аналітичні запити з об'єднаннями та агрегаціями (10 запитів у шарі `analytics/`, раніше `queries.py`), зовнішні ключі та унікальні обмеження. Додатково з'явилися вимоги privacy (згоди, аудит) з блокуванням рядків (`SELECT ... FOR UPDATE`).

## Розглянуті альтернативи

| Альтернатива | Плюси | Мінуси |
|---|---|---|
| SQLite | нуль налаштувань, файл у репозиторії | слабка підтримка паралельного запису, немає повноцінного блокування рядків, відрізняється від типового production |
| MongoDB (документна БД) | гнучка схема | зв'язки й агрегації між сутностями довелося б реалізовувати в коді, немає транзакційності на рівні реляційних обмежень за замовчуванням |
| **PostgreSQL** | транзакції, зовнішні ключі, блокування рядків, багаті агрегації, тип `Numeric` для грошей, JSON-поля | потрібен окремий сервер, складніше локальне налаштування |

## Рішення

Використовувати PostgreSQL через SQLAlchemy 1.4 / Flask-SQLAlchemy 2.5 і драйвер `psycopg2-binary`. Рядок підключення передається змінною `DATABASE_URL`.

## Наслідки

- (+) Цілісність даних гарантується схемою; грошові суми зберігаються як `Numeric(10, 2)`.
- (+) Privacy-модулі можуть використовувати блокування рядків для безпечних змін згод.
- (−) Для запуску й тестів потрібен працюючий PostgreSQL (див. README, швидкий старт).
- (−) Схема створюється `db.create_all()` без інструмента міграцій, зміни схеми вручну.
- (−) Бекап і відновлення стають окремим експлуатаційним завданням (див. ISD §7).
